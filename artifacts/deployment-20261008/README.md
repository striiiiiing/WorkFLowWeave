# 本轮发布版本的服务器验证与对比

本轮使用当时最新发布的运行层版本，继续此前四种部署方式的基准测试，排查公网 HTTP 访问失败，并在同一台计量服务器上逐一测试其他 Agent 产品。原始记录保存在本地的当前目录中。

## 范围与版本来源

- 目标服务器：通过 root SSH 直连用户所有的 `8.160.169.249`；`myserver` 仅作为独立的网络探测点，不是 SSH 跳板机。
- 本轮后端：`ghcr.io/striiiiiing/workflowweave-backend@sha256:d38ae390a4f751d30c24e9342abc06a96fd7e810064c74629a4cc4bef8a6f8d7`。
- 前端：`ghcr.io/striiiiiing/workflowweave-frontend@sha256:e5b4eb58bc27fbaae7bda91f1f3fdb8a7ccbe8f62008040a7a4af3c4ef77ebd1`。
- 测试开始时，服务器运行的是上一版后端 `657d84a17b7b`；本轮版本与上一版的应用文件和依赖版本相同，仅运行层顺序不同。
- 初始主机环境：Ubuntu 22.04、2 vCPU、1608 MiB 内存、无 swap、20 GiB 根文件系统；WorkFLowWeave 运行时约有 744 MiB 可用内存。
- 使用现有的较小 MSS TCP 辅助程序和 `curve25519-sha256` 算法，可以成功建立直连 SSH。辅助程序直接连接目标 IP，不经过中间服务器。

## 测量口径

沿用此前的基准测试定义：依赖已安装后启动进程三次，采样 60 秒空闲状态，再由四个客户端执行 60 秒健康检查与真实 `uname` 采集。CPU 的 100% 表示一颗逻辑核心；进程树 RSS 与 cgroup 工作集分别报告。原生和 Docker 部署使用同一份冻结的应用源码、依赖锁文件及完整渠道依赖。

其他产品逐一安装和启动。空闲占用、启动时间和磁盘数据仅用于比较部署情况，不表示功能相同，也不表示模型或工具工作负载相同。对比中未配置付费模型推理或真实消息平台账号。安装或启动失败也如实记录。

磁盘统计区分压缩产物、解压后的安装文件、Docker 镜像与存储占用、安装及构建缓存、持久化状态。共享层不能重复计算；每个产品均记录准确的源码或镜像版本，以及可选组件。

## 初始网络证据

- 上一轮在服务器本机执行 HTTP 健康检查成功。
- 从本地和 `myserver` 访问公网 HTTP，均返回 curl 错误 52（空响应）。
- 将 TCP MSS 分别设为 1000 和 800 后直接请求 HTTP，也在约 4.59 秒后返回零字节。
- 初始 Nginx 访问日志中只有服务器本机请求，没有外部探测请求。
- 主机 UFW 已启用，初始放行列表不含 3000 端口。这只是待排查的假设，尚未证实为故障原因。

## 网络排查与结果

与请求同步进行的抓包 [public-probe.txt](public-probe.txt) 和 [inbound-proof.txt](inbound-proof.txt)，分别观察到了无关的云代理流量和直连 SSH 入站流量，但均未发现公网 80/3000 端口探测流量入站。服务器本机通过回环地址或内网 IP 访问 3000 端口的健康接口，返回 HTTP 200；通过公网访问主机独立 Nginx 的 80 端口，同样返回 curl 52。因此，观察到的故障发生在流量到达主机之前；抓包尚不能确定具体是哪条安全组、NAT、服务商或客户端网络路径规则造成的。

主机 UFW 原先未放行 3000 端口，现已显式允许 `3000/tcp`，注释为 `WorkFLowWeave frontend`。这并未修复公网访问：[public-after-ufw.txt](public-after-ufw.txt) 仍记录 curl 52。排查期间从未关闭整个防火墙。本次会话无法访问云安全组，已向用户请求确认。现有网络证据不足以支持修改 Docker、前端或后端代码。

通过 TCP 辅助程序建立直连 SSH，再使用 SSH 隧道访问，可以得到 HTTP 200。Tabbit 浏览器访问公网地址时观察到 HTTP 502；通过隧道访问时已到达指定的 localhost URL，但浏览器页面在观察过程中被关闭。浏览器交互验收仍未完成，详见 [browser-evidence.md](browser-evidence.md)。Shell 中的 HTTP 检查不能替代浏览器验收。

后端、前端和运行环境镜像已推送至 Docker Hub 的 `striiiiiing` 命名空间。使用匿名仓库令牌验证了固定标签 `20261007T190805Z`、`latest`、`runtime` 和 `runtime-20261007T190805Z`。六个摘要均与 GHCR 一致，详见 [dockerhub-verification.json](dockerhub-verification.json) 及对应推送日志。凭据通过 Docker 现有的凭据辅助程序获取，未暴露。

## 对比产品的证据

固定版本的官方 amd64 镜像清单和源码发布版本记录在 [comparators.json](comparators.json) 中。[registry-summary.json](registry-summary.json) 记录去重后的压缩层内容大小，[layer-sizes.json](layer-sizes.json) 记录解压后的 tar 字节数，本地检查文件记录运行组件。这些字节统计口径不同于文件系统实际分配空间，也不同于 Docker 按镜像报告的存储占用。

最初通过 Docker Desktop 拉取镜像时，在 blob 重定向阶段因 EOF 失败。随后显式使用本地下载器，通过 Shell HTTP 代理下载，逐一校验 SHA-256，并生成 OCI 归档。OpenClaw 从其官方 Docker Hub 镜像源获取，amd64 镜像清单摘要一致。镜像归档通过 SSH 直接传输到目标服务器；下载或导入所用归档不计入最终部署占用。

| 官方镜像 | 下载层 / MiB | 未压缩层 tar / MiB | 本机 Docker 镜像存储 / GB（十进制） | 主要运行文件 |
| --- | --- | --- | --- | --- |
| OpenClaw 2026.9.8 | 1171.9 | 3242.6 | 4.96 | `/app/node_modules` 2634.4 MiB；`/app/dist` 352.7 MiB |
| Hermes v2026.9.24 | 923.0 | 2679.8 | 3.97 | Python 虚拟环境 382.0 MiB；Node 依赖 375.7 MiB；Playwright 浏览器 265.7 MiB；系统共享库 551.8 MiB |
| QwenPaw v2.2.1 | 947.1 | 2823.7 | 4.15 | Python 虚拟环境 948.0 MiB；系统 Chromium 337.8 MiB；GCC 119.3 MiB |

上述存储数据来自本机 Docker Desktop/containerd，与测量 WorkFLowWeave 完整栈镜像占用 0.936 GB（十进制）时使用的模式相同；目标服务器的实际存储增量在导入时另行采集。未压缩 tar 字节数不等于文件系统分配字节数，也不等于 Docker 报告的镜像存储占用，嵌套目录不能重复相加。运行组件记录见 [disk-components.json](disk-components.json)，这些只是 Shell 检查结果，不是产品在目标服务器上的运行测量。其他产品的标准镜像包含额外功能，不能据此认定产品功能等价。

OpenClaw 镜像已成功导入目标服务器。首次实际启动 Gateway 时，主机可用内存约为 245 MiB，但就绪检查尚未通过。随后直连 SSH 握手反复超时，独立探测点对 22 端口的服务标识探测也超时。尚未取回 OOM 或退出结果，因此不能将 OOM 写成已证实的原因。已请用户在条件允许时，通过云控制台停止 `wwcompare-openclaw`。Hermes/QwenPaw 的目标服务器测量仍待完成；本地预检不能替代目标服务器上的 CPU、内存和启动时间测量。

为给主机保留资源，测试运行器支持在后续目标服务器测试中显式记录并设置 768 MiB 内存上限（无 swap）和一颗核心的 CPU 上限。这是另一组有资源限制的部署条件，与未设限的 WorkFLowWeave 测量比较时必须说明。

本地预检：在 768 MiB 上限下，Hermes 的真实 Dashboard 通过 localhost 返回 HTTP 200（1802 字节）；QwenPaw 的真实服务在相同上限下也返回 HTTP 200。两个临时容器及其匿名卷均已删除。QwenPaw 的标准入口还会启动 Xvfb/Xfce/dbus，其官方镜像不只是 Python API 服务。详见已保存的本地预检日志。这些仅是启动与配置检查，不是目标主机上的对比测量。

截至本记录的验证结果：四项既有 Docker bootstrap 测试均在要求的 60 秒硬超时内通过；本轮脚本的 Ruff 检查、Compose 配置检查，以及本轮改动范围内的差异空白检查均通过。未因外部网络故障修改应用代码。

记录结束时的服务器状态：启动 OpenClaw 前已主动停止 WorkFLowWeave。目标服务器仍无法通过 SSH 访问，无法确认最终清理和 WorkFLowWeave 恢复情况。在恢复连接并重新检查健康状态之前，不能将最终部署描述为健康。
