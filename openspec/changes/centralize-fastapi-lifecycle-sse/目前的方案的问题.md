看了第二版实现。**主要问题是：旧 lifecycle 的职责和状态几乎完整保留，却把原来一个对象内部的协作，变成了多个文件通过 `app.state` 互相操作私有状态。文件拆开了，职责边界没有拆开，封装反而弱了。**

下面按影响列出具体问题，也区分哪些是新引入的结构问题、哪些是继承的旧问题。

1. **[P1] 准入控制有多个写入者，已经出现状态矛盾。**

   lifespan、reload、health 都能暂停和恢复 Workflow 准入。尤其 [operations.py:89](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/operations.py:89) 的外层异常处理会恢复准入，但内部重载失败已经设置了“必须恢复后才能运行”。

   我实际复现得到：

   ```text
   recovery_required = True
   workflow_accepting = True
   agent_accepting = True
   scheduler_paused = True
   ```

   应用一边声明需要恢复，一边允许新任务进入。**这个错误旧版就存在，第二版把相关控制拆散后仍原样保留。**根因是没有唯一的准入决策者，各处自己恢复状态。

2. **[P2] `RuntimeState` 是被拆掉方法的旧 lifecycle，多个模块绕过封装操作它。**

   [state.py:59](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/state.py:59) 仍保存启动任务、关闭任务、清理任务、全局锁、各组件所有权和重载标志；lifespan、operations、health 直接读写这些 `_private` 字段。

   原来修改一条生命周期规则，主要在一个类里理解。现在必须同时检查三个模块：谁持锁、谁设置标志、谁恢复准入、谁清空引用。**这是把一个过大的对象拆成了分布在多个文件里的同一个对象。**

3. **[P2] `app.state` 变成内部总线，资源访问出现两套路径。**

   资源同时存在于 `state.runtime._workflow` 和 `state.services.workflow` 等位置，见 [lifespan.py:185](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/lifespan.py:185) 与 [services.py:29](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/services.py:29)。

   启动阶段需要记录部分已创建资源，这有合理性；问题是启动完成后，reload 回调继续访问 runtime 的所有权记录，路由和 health 访问 services。清理时又逐个清空 runtime，最后才撤下 services。它们的用途和有效阶段没有被接口约束，维护者必须自行保证两边一致。

   FastAPI 的 `app.state` 只提供存储，不能替我们保证这些一致性。

4. **[P2] health 被当作依赖计算，却承担应用控制。**

   [dependencies.py:23](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/dependencies.py:23) 调用健康报告函数，但 [health.py:272](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/health.py:272) 实际会暂停、恢复 Workflow。

   因此访问健康接口会改变运行准入；不访问时，这条检查路径不会执行。它还独立于生命周期锁运行。**这也是继承的旧问题，并未完成任务记录所说的“只读探测与准入判定”职责收敛。**

5. **[P2] FastAPI DI 没有收窄依赖，路由仍拿到整个应用并操作业务内部。**

   [dependencies.py:14](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/dependencies.py:14) 只有一个返回全部服务的 `get_services`。Agent 路由仍读取 `_session_view`、取得 scheduler 锁、组装 workspace identity、写入事件日志，见 [agent_routers.py:62](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/agent_routers.py:62)。

   `Depends` 接入了，但请求依赖边界仍很宽。这里真正需要的是直接注入所需服务，并把 Agent 的文件操作及一致性规则留在 Agent 自身，而不是再增加一套 API facade。

另外，当前 [lifespan.py:1](/mnt/d/code/WorkFLowWeave/src/workflowweave/interaction/fastapi/lifespan.py:1) 多了一个 `z`，应用无法导入。编译、Ruff 和边界测试收集均失败。这是独立的语法问题，不能解释上述架构缺陷；任务记录里的历史通过结果也不能代表当前工作区。

**为什么这次重构会走成这样？**实施把“删除 `ApplicationLifecycle` 类”和“使用 FastAPI API”当成了完成标准，却没有先定义三个关键约束：谁唯一决定准入、谁拥有资源、其他模块通过什么有限接口访问状态。我之前写的设计也有这个缺口，列了框架机制，却没有明确这些约束。

修正方向应当是先收敛这三个责任：lifespan 管资源取得和释放，重载协调有明确接口，准入变更集中在一处；`app.state` 保存已装配对象，路由通过窄依赖访问。原生 SSE 的接入和订阅清理可以保留。**现在继续加方案三的 facade，会把这些问题再包一层，无法解决根因。**
