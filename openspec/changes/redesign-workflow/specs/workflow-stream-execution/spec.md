# Workflow 流式执行

## Purpose

以内容 state 和 checkpoint 保存执行事实，由 astream_events 订阅者归档长期结果并提供必要业务进度，使前端在其他分支仍执行时看到已提交结果；checkpoint 清理后仍能按固定业务版本读取归档。BackupPolicy 统一管理执行副本和归档数据的保留；正文备份开关控制长期归档，不禁止执行 checkpoint 保存内容。

## Scope

本轮确认内部原生事件消费、存储和逐项业务进度。对外 snapshot 的首帧、版本传输、心跳、断连和离页行为依据 design 第 4 节继续讨论；此前具体 SSE 场景不作为本轮新结构已确认的传输契约。本文的固定业务版本和逐项可查询要求保持。

## ADDED Requirements

### Requirement: 统一的执行过程输出

系统 SHALL 使用一次 `astream_events` 提供父图及子图的原生过程事件，由图内 tags 标识业务类别，通过 `config.metadata.sessionID` 关联 session，且与 checkpointer 的 thread_id 一致。订阅者 SHALL 从事件 metadata 和原生调用信息识别运行，不根据先前消息猜 session，不各自启动新的图事件源。

#### Scenario: 分支乱序完成

- **WHEN** 多个采集或分析任务以不同顺序完成
- **THEN** 先完成的结果先独立保存和发布，中间数组可按完成顺序排列，前端自行排序；最终业务结果遵循配置顺序

#### Scenario: 多个内部消费者观察同一运行

- **WHEN** 存储和其他内部消费功能同时订阅同一运行
- **THEN** 共享一次执行产生的原生事件，新增订阅不会新增采集、模型调用或通知发送

#### Scenario: 并发运行共用分类 tags

- **WHEN** 两个 session 的节点具有相同 tags 且事件交错到达
- **THEN** 订阅者依据各事件 metadata.sessionID 区分运行，存储的 session 与 checkpoint thread_id 一致，不串写结果

#### Scenario: tags 传播到嵌套调用

- **WHEN** 业务节点的模型或内部 Runnable 继承同一 tag
- **THEN** 消费者按对应业务完成边界处理，不能把每个继承 tag 的内部调用都归档为一项新结果

#### Scenario: 原生 checkpoint 载荷

- **WHEN** 原生事件流输出图的 checkpoint 投影
- **THEN** 消费者从实际图事件载荷读取 config、namespace 和状态等信息，不要求框架不存在的 on_checkpoint 事件，不把每个普通 chain stream 都视为 checkpoint

### Requirement: 选择必要业务事件实时推送

系统 SHALL 通过 `astream_events` 消费子模块，按 tags 所标识的业务类别选择 fan-out 单项成功、业务 fan-in 完成、aggregate 成功和逐渠道发送成功更新，及时推送前端；不得等待整个子图结束，也不得默认广播所有内部节点。事件 SHALL 关联 session、执行轮次、类别和稳定业务身份，允许协程调度及传输耗时。

#### Scenario: fan-out 单项先完成

- **WHEN** 某个采集或分析项完成必要业务提交，而另一个分支仍被阻塞
- **THEN** 消费者先提交该项归档并推送，前端在其他分支结束及 arrange 执行之前看到该项成功，不因声明位置靠后等待；展示排序由前端处理

#### Scenario: fan-in 完成

- **WHEN** 业务 fan-in 完成汇总
- **THEN** 前端收到一次对应结果更新，父子图重复暴露结果不生成重复条目或业务版本

#### Scenario: aggregate 成功

- **WHEN** aggregate 完成必要业务提交并冻结输出，包括关闭模型 fan-in、仅整理分支输出的情况
- **THEN** 前端收到一次 aggregate 成功更新，不等待 notify 完成

#### Scenario: fan-in 与 aggregate 完成点区分

- **WHEN** fan-in 和 aggregate 分别完成各自的业务工作
- **THEN** 分别推送对应完成结果；若两种分类实际指向同一个完成结果，则只推送一次并明确 aggregate 成功，不因分类去重而漏报该阶段完成

#### Scenario: 单渠道发送成功

- **WHEN** 一个 output/channel 投递项发送成功且确定回执已持久化，而其他渠道尚未完成
- **THEN** 前端立即进入可异步推送该项成功的路径，不等待整个 notify 子图完成

#### Scenario: 不推送内部节点

- **WHEN** 初始化、路由、intent 或仅负责排序的内部节点完成
- **THEN** 不因此生成前端业务完成事件，不将这些节点与业务 fan-in 混淆

#### Scenario: 业务失败或不确定投递

- **WHEN** 选定业务项返回 failed 或 delivery_uncertain
- **THEN** 前端收到相应错误或不确定状态，不因节点正常返回而显示成功

#### Scenario: 相同 tags 与订阅重连

- **WHEN** 多个分支共享分类 tags，或前端断线后重新订阅
- **THEN** 各项按稳定业务身份归档和展示，已提交状态可从存储按 session 和固定版本查询，不串项或重新执行原运行；对外重连的具体传输协议另行确定

### Requirement: 最小内容 state 与执行权威

系统 SHALL 在 state、checkpoint 和 pending writes 中保存执行所需的真实内容，以 checkpoint 和已提交任务 writes 作为唯一执行权威。节点 SHALL 只读取必要 state、调用能力并返回结果，不读取或写入 SessionStore，不以外部正文引用代替内容。当前 state SHALL 避免重复正文表示并释放下游不再需要的字段；不得以截断正文或丢失配置输入满足精简目标。

#### Scenario: 通知读取冻结输出

- **WHEN** 一个输出发往多个渠道
- **THEN** 各投递按 output ID 使用当前 state 中的同一份冻结正文，意图和回执不各自复制正文，也不从归档恢复输入

#### Scenario: 阶段结束后收缩 state

- **WHEN** 某阶段内容已不被下游使用
- **THEN** 当前 state 可明确移除该字段，历史持久化副本保留至归档交接完成；仍保留原父图阶段入口所需输入

### Requirement: 流消费形成长期归档

系统 SHALL 以单次 astream_events 驱动归档，对每项结果确认对应 checkpoint 或 pending writes 已提交后，按稳定事实身份幂等写入长期正文、摘要、可用性与业务版本。SessionStore SHALL 是执行事实的派生归档，不决定图的下一步或反向覆盖 state。归档事务提交后才可发布相应可读结果，不把 checkpoint ID 当作业务版本。

#### Scenario: 流更新早于持久化完成

- **WHEN** 消费者已收到某个节点更新，但对应任务提交尚未确认
- **THEN** 不将普通节点完成回调直接当成持久化确认，不发布未经归档的可读正文，不因此允许清理源数据；正常消费不得为每条事件全量扫描该 session 的历史 checkpoint

#### Scenario: 一项已提交且其他项仍执行

- **WHEN** 一个分支的成功 pending writes 已确认持久化，而兄弟任务尚未完成
- **THEN** 消费者独立归档并发布该项，不等待整个 superstep 或子图结束

#### Scenario: 慢存储消费

- **WHEN** 存储订阅的处理速度低于事件产生速度
- **THEN** 分发按所选机制显式背压，不静默丢存储事件，不建立无界任务或无限正文缓存；若采用队列，其容量必须有界

#### Scenario: 子图清理后的固定版本查询

- **WHEN** 已完成子图内部 checkpoint 被清理，业务正文仍在保留期内
- **THEN** Agent 和历史消费者仍可通过 SessionReader 读取指定业务版本的正文

#### Scenario: 旧正文过期

- **WHEN** 指定业务版本正文已过期，新轮次产生了新正文
- **THEN** 返回旧正文不可用，不用新正文替代或从 checkpoint 恢复旧正文副本

### Requirement: 独立任务恢复

系统 SHALL 保持逐来源、逐分析项的独立图任务边界，在同一轮进程中断续跑时复用已持久化成功结果。用户主动从阶段重跑时，目标阶段及后续任务重新执行；本要求不承诺单独重试一个已经正常返回 failed 的业务节点。

#### Scenario: 一个分支中断而另一个已经保存

- **WHEN** 进程在某个子图任务执行中中断，另一分支的成功结果已持久化，随后在原轮次续跑
- **THEN** 已保存成功结果被复用，未完成任务继续执行

#### Scenario: 恢复材料缺失

- **WHEN** 原 checkpoint 或必要的原配置、正文不可用
- **THEN** 恢复明确报告原因，不以重新采集或当前配置补齐旧运行

### Requirement: 三类正文独立归档与索引

系统 SHALL 将采集结果、分析结果和最终报告保存为三个可独立读取、保留和清理的正文集合，通过共用索引关联 session、epoch、业务身份、固定 content_version、来源、摘要、可用性及过期时间；不得只保存一份包含全部上游正文的全量运行对象。归档引用 SHALL 不改变执行 state 保存真实内容的要求。

#### Scenario: 采集正文过期而分析与报告仍保留

- **WHEN** 某轮采集结果已过期，分析结果和最终报告尚未过期
- **THEN** 采集固定版本返回 expired，分析和报告仍独立可读；上游索引保留，不级联删除下游或从下游副本恢复采集正文

#### Scenario: 逐项结果与阶段读取

- **WHEN** 多个采集/分析项分别完成归档
- **THEN** 每项按稳定身份归档，阶段读取按共用索引和配置顺序组合，不重复保存完整 state 或全阶段正文副本

### Requirement: 不可变提示词版本复用

系统 SHALL 对相同的静态系统提示词和模板按内容及格式版本去重，归档结果关联本次实际使用的不可变版本、模型/参数及上游身份；修改现行配置不得改变旧结果的来源解释。业务输入 SHALL 不作为永久共享提示词保存以绕过正文过期，提示词正文遵循 snapshot 备份开关。

#### Scenario: 多个运行使用同一提示词

- **WHEN** 多个结果使用内容及格式版本相同的系统提示词
- **THEN** 长期归档复用同一提示词内容记录，每个结果保留自己的关联、业务身份和正文，不重复复制提示词

#### Scenario: 提示词修改后读取旧结果

- **WHEN** 新运行采用修改后的提示词，用户查询旧版本结果的来源
- **THEN** 旧结果仍关联原提示词版本，不通过当前配置名称替换旧内容

#### Scenario: 原始输入过期或配置备份关闭

- **WHEN** 动态提示词包含的原始采集输入已过期，或该运行关闭 snapshot 备份
- **THEN** 不通过共享提示词/渲染请求偷偷保存或重新公开禁止保留的内容；明确呈现缺失来源材料，不承诺完整重建模型请求

#### Scenario: 某类正文清理后提示词仍被引用

- **WHEN** 一份采集或分析正文被删除，但其他保留的报告/追溯索引仍引用同一提示词
- **THEN** 共用提示词记录仍保留，不能随最早过期正文一起删除

### Requirement: BackupPolicy 统一管理数据保留

系统 SHALL 使用 BackupPolicy 统一管理 checkpoint 保留期、配置快照/共享静态提示词的归档与关联保留、采集/分析/最终报告的归档开关与独立期限。通知 intent/receipt、来源索引、摘要及版本/可用性 SHALL 作为必要记录随关联运行、结果和追溯关系管理，不建立平行策略或逐项备份开关。

#### Scenario: 关闭可选正文归档

- **WHEN** BackupPolicy.enabled=false 或某类正文归档关闭
- **THEN** 执行仍保存必要 checkpoint，按其独立保留期管理；归档保留必要管理事实及 not_saved，不保存被关闭的正文，也不通过共享提示词表绕过 snapshot 开关

#### Scenario: 正文过期后的关联记录

- **WHEN** 某类正文到期而结果身份或其他结果的追溯关系仍需保留
- **THEN** 删除该类正文，保留必要投递事实、来源索引、摘要和 expired 标记；共享静态提示词仍有保留引用时继续保留，无引用后才可回收

### Requirement: 分层保留期

系统 SHALL 在 storage 所有的 BackupPolicy 中分别独立配置 checkpoint、采集结果、分析结果和最终报告的保留期；checkpoint SHALL 默认 7 天，采集 SHALL 默认 30 天，分析和最终报告 SHALL 默认不过期。通常 checkpoint 较短、采集其次、分析和报告较长，仅为使用建议；系统 SHALL 不按类别间期限顺序拒绝配置或自动联动修改其他类别。

#### Scenario: 未显式配置保留期限

- **WHEN** 新运行使用默认 BackupPolicy
- **THEN** 按该轮共同时间起点计算 checkpoint 7 天、采集 30 天的截止时间，分析和最终报告没有默认过期时间；所有配置入口复用同一默认值

#### Scenario: 服务持续运行且没有新任务

- **WHEN** 非活动运行的内容已经到期且归档交接完成，服务未重启且没有新的运行退出
- **THEN** 仍可由生命周期过期检查触发相应删除，不必须等待该 session 再次执行或应用重启

#### Scenario: 默认长期结果保留

- **WHEN** 分析和最终报告未配置有限保留期，而 checkpoint 和采集已依次到期
- **THEN** 分析和最终报告继续可读，不被旧统一 retention_days 或其他类别的清理删除

#### Scenario: 用户独立指定保留期

- **WHEN** 用户给多个类别设置相同期限，或让分析保留时间长于最终报告等与通常顺序不同的配置
- **THEN** 系统按各类有效配置分别处理，不因大小关系拒绝或调整期限

#### Scenario: 统一时间基准与迟到归档

- **WHEN** 同一轮次正常结束或确认中断后确定保留期起点，消费者稍后补齐归档
- **THEN** 四类期限按该轮共同起点计算；迟到归档、重复消费或同轮续跑不重置已确定截止时间，未结束的活动执行受清理保护

#### Scenario: 过期后的固定版本与重放

- **WHEN** 指定正文已过期，同一事实又被归档消费者观察到
- **THEN** 保留原身份、版本和 expired 标记，不重新插入正文或重新计算期限；查询视图反映新的可用性

#### Scenario: 旧归档迁移到分类存储

- **WHEN** 已有业务归档迁移或重新建立索引
- **THEN** 保留原版本和已确定截止时间，不将过期正文复活；旧统一期限到新分类配置的变化必须明确呈现

### Requirement: 执行事实与观察一致

系统 SHALL 以已提交的执行状态及业务事实提供查询，重复消费同一结果不得增加业务版本；不得以流事件到达替代持久化完成。

#### Scenario: 同一结果从父子图重复出现

- **WHEN** 消费者观察到指向同一已保存业务结果的多个更新
- **THEN** 相同事实键和相同内容复用原业务版本，不重复归档正文；同键不同内容明确报错

#### Scenario: 必要持久化失败

- **WHEN** 恢复所需数据或必要管理事实无法提交
- **THEN** 系统显式记录或向调用方报告失败，不继续依赖未提交事实的新外部操作

#### Scenario: 归档失败而 checkpoint 已提交

- **WHEN** 长期归档写入失败
- **THEN** 系统显式报告归档错误、保留源数据并阻止清理，不把该项已有业务结果改写为业务失败；必要消费者无法继续安全接收结果时停止执行驱动并保留恢复材料

#### Scenario: 消费遗漏或归档后进程退出

- **WHEN** 进程在任务持久化后、归档前退出，或已归档但未记录内存消费位置时退出
- **THEN** 启动或续跑从保留的 checkpoint/writes 使用同一归档路径补齐，幂等复用已归档版本，不重做业务，也不假设重开 astream_events 会重放全部历史

### Requirement: 保持既有外部契约

系统 SHALL 保留已保存配置的业务执行含义及只读历史的固定业务版本；备份开关按本次明确变更控制长期归档，配置说明与界面 SHALL 同步说明 checkpoint 内容保留边界。本次内部图重构不要求 Collector、AI 或 Channel 插件改用新协议。

#### Scenario: 使用现有配置和历史消费者

- **WHEN** 已有 Workflow 执行，History Collector 或 Agent 接续读取指定版本的结果
- **THEN** 原提示词、输入顺序及查询语义保持有效，消费者不需要解释 checkpoint 私有表

#### Scenario: 某类正文关闭备份

- **WHEN** 配置关闭某类正文的长期备份
- **THEN** 该正文仍可进入执行 checkpoint/pending writes；长期归档只提交必要摘要、版本和 not_saved 标记，历史读取不通过 checkpoint 绕过开关

#### Scenario: 归档正文到期但恢复入口仍保留

- **WHEN** 某固定业务版本已过期，而某个保留的阶段入口仍包含执行内容
- **THEN** 历史读取返回 expired，不从 checkpoint 重新公开正文；系统不宣称执行副本已从磁盘彻底删除

#### Scenario: 旧运行执行位置与新图不兼容

- **WHEN** 旧 checkpoint 包含新图无法解释的节点或任务位置
- **THEN** 系统明确报告不兼容并保留历史，不猜测执行位置或自动重发通知

### Requirement: Workflow 运行视图逐项更新

前端 SHALL 在 Workflow 运行详情普通模式展示当前阶段与逐项业务进度，按稳定业务 ID 渲染条目，并由前端依据原配置顺序信息进行简单展示排序；用户无需手动刷新、打开高级模式或等待整个阶段结束。运行成功、业务项成功、正文可用性和连接状态 SHALL 分别呈现，不相互替代。

#### Scenario: 从 Workflow 列表发起运行

- **WHEN** 用户点击立即运行并进入该 session 的详情，某个采集或分析项成功而兄弟项仍执行
- **THEN** 页面直接显示已成功条目和其余未完成状态，允许中间数组顺序不同；前端以稳定 ID 处理列表插入和排序，不等待其他项完成，不要求刷新或展开技术信息

#### Scenario: 汇总已完成但通知仍进行

- **WHEN** aggregate 成功并发布可读取的固定版本报告，而一个通知渠道仍未完成
- **THEN** 前端可以展示该报告并继续更新各通知投递，运行整体仍显示真实执行状态，不提前显示全部完成

#### Scenario: 成功项没有可保存的正文

- **WHEN** 一个业务项已成功，但正文未保存或已过期
- **THEN** 页面显示该项真实结果、摘要及正文不可用原因，不将正文缺失解释为任务未完成，也不用其他版本正文替代

#### Scenario: 运行按策略提前结束或没有通知目标

- **WHEN** 运行按既有失败或空结果策略结束，或没有可发送的输出与渠道
- **THEN** 页面反映真实结束状态，不把未执行步骤显示为成功，也不持续等待不存在的投递

### Requirement: 存储提供统一的只读结果

系统 SHALL 由 storage 为 HTTP、Agent、History Collector 及内部订阅提供按 session 和固定业务版本查询的接口，包括逐项结果、正文可用性及必要报告组装；不得要求外部读取者通过执行层拼装报告、解释 checkpoint 私有表或再次驱动图。

#### Scenario: 多种调用方读取同一结果

- **WHEN** HTTP 与 Agent 查询同一 session 和同一业务版本
- **THEN** 使用相同存储查询语义，得到一致的业务结果及正文可用性，不各自维护结果副本

#### Scenario: 报告来自长期归档

- **WHEN** 执行 checkpoint 已安全清理，但需要组装的业务正文仍在保留期内
- **THEN** storage 可组装对应历史报告，执行层和事件发送端不参与跨阶段正文重建

### Requirement: 事实追加和生命周期删除

系统 SHALL 通过 storage 统一追加事实、查询及过期删除；业务事实一旦产生不得通过通用 Update 覆盖，主动阶段重跑追加新轮次，重复观察复用原版本。正文到期后的可用性变化 SHALL 不修改原始业务内容或用新轮次结果替代旧结果。

#### Scenario: 阶段重跑产生新结果

- **WHEN** 原 session 的某阶段主动重新执行
- **THEN** 新结果按新轮次追加，旧版本仍按其原保留策略查询，不通过覆盖旧正文实现重跑

#### Scenario: 多个订阅重复追加同一事实

- **WHEN** 父子图事件或不同分类指向同一已存在结果
- **THEN** storage 统一处理重复追加并返回原版本，不由每个订阅者生成另一套版本或归档副本

### Requirement: 按功能与职责验收架构修改

系统实现 SHALL 保留本变更约定的功能和持久化边界，按 storage、graph、execution、stream 分离存储、构图、执行和消费职责，删除被替代的引用执行路径、节点归档包装、重复标记注册表及逐事件全历史扫描。外部 snapshot/重连协议待后续确认，不以旧传输方案的细节作为本轮内部重构验收条件。新增代码 SHALL 对应明确的业务或可靠性职责；不要求物理行、非空行或生产代码总量低于任何历史基线。

#### Scenario: 新增功能导致代码增长

- **WHEN** 实现分类归档、恢复、保留策略或实时展示等约定能力导致生产代码增长
- **THEN** 按功能正确性、职责边界和重复实现是否移除验收，不因行数增加判定失败，也不为压缩行数削弱功能

#### Scenario: 使用既有运行触发方式

- **WHEN** 手工触发、间隔、cron 或一次性定时触发已有 Workflow
- **THEN** 统一进入执行入口，保留原运行准入、取消/等待和调度行为，不因模块迁移形成两套图内调度实现
