## 2. 收发与指令

- [x] 2.2 同一实例的不同好友/群/发送者只进入该实例绑定的对话；未绑定时明确报告，不自动建对话。

## 决策依据与默认值

| 决策 | 依据 |
| --- | --- |
| 一个渠道实例至多一个当前对话 | 用户本轮两次明确确认；实例 ID 与插件能力名不同，同能力允许多个实例。 |
| 初始未绑定 | 用户要求无默认渠道，后续纠正为渠道持有对话；不自动选历史会话或从第一条普通消息建会话。 |
| 不增加 AgentSession.channel_id | 用户明确对话不知道所属渠道，发送时由渠道侧确认。 |
| 不使用 wait_result | 用户要求接收只入协程队列，送达确认属于 Workflow send；Web 自身仍需兼容原响应。 |
| 复用现有队列与发送 | QwenPaw manager 的 enqueue/消费者和 base 的发送入口提供职责参考；本仓库已有 UnifiedQueue、Agent 命令端口和 Workflow 通知执行器。 |
| 保留平台来源身份 | 一个实例绑定一个对话不表示不同对端可以共用回复地址或消息去重键。 |
| Web 与绑定共存 | 用户明确要求绑定渠道后仍可通过 Web 调试，Agent 原日志继续唯一。 |

## 5. 本次设计补充的实施任务

依据：用户最新要求“/resume 可以修改绑定的对话 ID”“采用内存进行缓存维护”“改绑先写到内存”“线程有锁”，对应 design 第 2.1、3、4 节；此处追加任务，保留原任务记录。

- [x] 5.1 启动加载实例绑定缓存；所有读取使用线程锁和不可变快照，入站与发送检查不查询 SQLite。
- [x] 5.2 异步写锁串行改绑，先更新加锁内存，再持久化 SQLite；持久化失败显式报错、恢复之前对话并推进版本，回滚事务。
- [x] 5.3 `/resume <session_id>` 允许改绑任意存在的 Agent 对话，删除旧 peer ownership 限制，验证不存在目标不改变绑定。
- [x] 5.4 验证内存先更新、读取不执行 SQL、并发写串行、失败恢复与改回原 ID 时旧输入/输出仍过期。

实施选择：复用 `ChannelBindings` 的 SQLite 文件，增加 `instance_bindings` 表，避免改变旧 `peers` 的非空约束或猜测旧对端绑定。新表仅存实例 ID、session 和版本；内存缓存是运行时路由来源，表是其恢复记录。API 为 `GET/PUT /api/channels/{id}/conversation`，请求与响应使用 `{session_id: string|null}`，不在 ChannelConfig 内维护重复绑定。缓存线程锁不跨 await，已有异步锁串行持久化，处理端的实例锁协调短命令准入与界面改绑。

## 6. 收尾审查补充任务

依据：design 2.1 的内存/磁盘一致性及第 4 节发送确认；aiosqlite 在 worker 线程执行 SQL，取消等待不等于取消 SQL。

- [x] 6.1 保护已开始的绑定持久化事务，调用者取消时等待事务完成并传播取消；验证缓存与磁盘一致，写锁不提前释放。SQLite 写失败映射明确 storage_failed。
- [x] 6.2 发送配置检查使用保留的实例配置，不将 suspend 移除接收列表误当作改绑；验证正常关机最后回复仍排空。

切换屏障的简单版本：屏障之前输入完成于原对话；已入队且携带旧版本的屏障之后输入明确失败，不自动转投。切换完成后新入队消息进入新对话，依据 design 第 4 节旧排队输入不能转投的要求。

## 7. 用户最终确认的频率与持久化取舍

依据：用户 2026-10-05 明确“改绑是低频，应该同步；查询发送位置是高频，只依据内存版本，内存有错误相对可接受”。

- [x] 7.1 保持先内存、后 await SQLite commit、完成后响应的改绑顺序；高频路由与发送检查仅调用加锁缓存，不引入后台持久化队列或逐次 SQL 对账。

`asyncio` await 表示本次调用等待完成，不表示先响应后后台保存；aiosqlite 已用内部线程执行 SQL。取消保护的短任务始终在本次调用和写锁内等待完成，不是 fire-and-forget 写入器。平台请求去重证据仍按已有设计使用数据库，不与“绑定路由只查内存”混为一谈。

## 源码参考结论

已查阅三个项目：[持久化与切换研究](persistence-research.md)。CC-Connect 的切换路径先改内存、同步尝试保存，再回复；当前 Codex 有顺序 writer 和显式 flush barrier，不能据底层入队推断外层响应一定先于持久化；Claude Code 只能从官方 changelog 证明异步 transcript 写入，核心顺序无法从公开仓库确认。本项目按用户最终要求保持低频改绑同步完成、高频发送查内存，不引入后台 writer。
