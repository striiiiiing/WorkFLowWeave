# 配置与资源管理模块：提案

## 1. 背景与目标

依据 [总体提案](../../proposal.md) §2、§3 和 [总体设计](../../design.md) §1、§3.1–§3.2，统一管理 JSON 配置与可复用资源。
数据源、Setter 模板、AI 配置、Channel 实例和 Workflow 定义需要稳定标识与明确引用关系。
每次运行使用独立的有效配置快照，后续修改资源不得改变已启动或历史 session 的含义。

## 2. 首版范围

- 提供严格的公共配置、结果、状态和错误模型，作为七个模块的共同契约。
- 读取系统级 JSON，解析数据目录、插件目录、日志路径和服务运行限制。
- 以配置文件所在目录解析相对路径，避免从不同工作目录启动产生不同结果。
- 持久化 `sources/setters/ai/channels/workflows` 五类资源。
- 提供协程形式的保存、读取、列表、删除和 Workflow 快照入口。
- 拒绝未知字段、非法 ID、无效枚举、非法数值及不完整的结构配置。
- 保存 Collector 的来源专属配置与声明的 Setter，业务语义由对应模块校验。
- 校验资源引用，阻止删除仍被 Workflow 或来源实例引用的资源。
- 展开同一 Collector 的 Setter 模板，实例同名值覆盖模板值。
- 为运行返回 `WorkflowSnapshot`，完整包含 Workflow、来源、AI、Channel 与创建时间。
- 配置写入使用同目录临时文件及原子替换，读取返回独立模型对象。

## 3. 职责边界

本模块负责结构校验、资源存取、引用一致性及快照，不执行 Collector、模型请求或通知。
Collector options/Setter 的能力校验、AI 提供方校验和 Channel 通知能力校验由所属模块负责。
Workflow 在保存和触发前组织完整业务校验，API 与 CLI 不各自实现一套规则。
插件同名 JSON 属于插件级配置，发现模块通过 `registry.plugin_config` 交给插件注册入口。
系统级配置中的目录与运行限制不会被插件级配置反向覆盖。
本模块产生快照对象；快照的持久化、保留期限和恢复读取由存档模块负责。
凭据仅保存环境变量名，不把运行时解析出的秘密写入资源文件或快照。
首版不提供认证服务、配置数据库、多进程写入协调或复杂配置热更新。

## 4. 验收标准

- [ ] 从不同当前目录加载同一配置文件，解析出的数据、插件和日志路径一致。
- [ ] 五类资源可保存、查询、列出与删除，重建 Store 后内容仍可读取。
- [ ] 未知字段、非法 ID、无效策略和非正数并发/超时得到带字段路径的校验错误。
- [ ] `temperature`、`top_k` 在 AI 配置及 `model_options` 中均被拒绝。
- [ ] 缺失来源、模板、AI、Channel 引用和模板 Collector 不匹配不能形成运行快照。
- [ ] 删除被引用资源返回冲突，并且原资源文件仍然存在。
- [ ] 实例 Setter 覆盖模板同名值，模板原对象保持不变。
- [ ] 快照包含 fan-out 和可选 fan-in 使用的全部 AI 配置，且返回统一模型类型。
- [ ] 修改源资源或返回对象不改变已有快照及 Store 中已保存的配置。
- [ ] 原子替换前的写入失败不会损坏上一版有效配置，不留下可读取的半文件。
- [ ] 并发保存与快照读取使用同一操作锁，快照不会混合一次操作前后的配置。
- [ ] 异步调用中的磁盘等待移交工作线程，错误信息不包含秘密或内部堆栈。

## 5. 交付与依赖

交付 `logagent/models.py`、`logagent/config.py` 及对应模块测试。
这是首个基础模块，不依赖 Workflow、Collector、AI、Channel 的具体实现。
其余模块依赖本模块模型；动态插件语义校验通过所属模块接入。
先完成本模块设计、三层 `tasks.md`、实现与测试，再按用户要求独立提交。
后继版本通过显式字段扩展模型，维持首版 JSON 与历史快照的兼容边界。
