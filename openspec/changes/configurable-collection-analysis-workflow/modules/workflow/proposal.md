# Workflow 模块提案（v0.1）

关联：[根 proposal](../../proposal.md) §2.1「WorkFlow 模块」、§3 验收标准 3–6/8，[根设计](../../design.md) §3.6，[模块设计](./design.md)。

## 1. 背景与目标

用户需要把多个固定来源编排成共享输入，交给不同 AI 任务分析，再按指定顺序汇总和通知。Workflow 模块提供完整应用入口，统一处理配置有效性、运行顺序、失败策略及按原 session 恢复。

首版以单进程和有界协程并发支持低资源部署。定时及手动触发共用运行入口；采集内容、分析结果和最终输出统一关联 session。

## 2. 本期范围

- 以有序资源 ID 配置来源、AI 任务和通知目标，保存与触发前执行完整语义校验。
- 通过 `WorkflowSnapshot` 固定原 Workflow、展开 Setter 的来源、AI、Channel 和快照时间。
- 使用 LangGraph 执行 `collect → analyze → aggregate → notify → finish`。
- 分别处理来源错误、缺失、原始空、处理后空及全空，保留准确状态和 Collector 计数。
- 将唯一完整共享输入交给所有分析分支，按配置限制采集与分析并发，并保持声明顺序。
- 支持可选 fan-in，原输入只能作为整体放入一个位置；可进一步调用 AI 或分别输出分支结果。
- 支持部分失败策略、多目标有序通知、逐投递即时保存回执。
- 实现手动触发、单 Workflow 不重叠的定时触发、等待、取消、恢复和服务关闭。
- 按备份范围保存内容，明确报告关闭、过期、损坏、缺失或写入失败导致的恢复限制。

## 3. 明确边界

所有首版分析分支使用同一份输入。来源子集、Agent 分支、Webhook、健康监听和流程评估属于后续版本，本期不接受这些尚未实现的配置。

恢复使用原快照和原存档，不能重新采集来源、重跑成功分支或重新发送已有成功回执的通知。缺少必要材料必须报告不可恢复范围。

最终输出进入通知阶段后冻结，恢复只补失败或未完成的投递；需要改变已发布分析时，通过新触发创建新 session。SMTP 等外部投递可能存在确认不确定性，保留诊断，不承诺跨外部系统的 exactly-once。

Workflow 只调用 Collector、AI、Channel 和 ArchiveStore 的公开入口，不自行实现插件协议或直接替换它们的存储策略。

## 4. 验收标准

| 编号 | 可验证行为 |
| --- | --- |
| WF-01 | 无效资源、Setter、模型、通知能力或顺序在保存/触发前被拒绝。 |
| WF-02 | 多个来源形成一份有序输入，所有分析分支逐字收到同一文本。 |
| WF-03 | 并发上限为 1 时实际串行，较大时允许并行；单来源或单分支超时有界。 |
| WF-04 | 原始空、处理后空、缺失和失败各自执行对应策略；全空 `skip` 不调用 AI 或通知。 |
| WF-05 | fan-in 开关、顺序、原输入位置、失败标记和部分发送策略符合配置。 |
| WF-06 | 输入、分析和最终结果按 session 保存；备份降级不被误报为可完整恢复。 |
| WF-07 | 修改资源后恢复仍用原快照，不增加原来源或成功分支调用次数。 |
| WF-08 | 通知部分失败后只补未成功组合，已冻结输出和成功通知保持不变。 |
| WF-09 | 定时任务不重叠、不补全部错过周期；取消/关闭后无新增通知和遗留任务。 |
| WF-10 | 完成十分钟离线稳定性运行，记录资源占用、次数和未处理异常，报告来自实际执行。 |

## 5. 依赖、产物与实施边界

依赖配置、存档、Collector、AI、Channel 五个模块和公共模型。交互模块调用 `WorkflowService`；后续控制 Channel 也复用相同入口。

预期代码位于 `logagent/workflow/`，测试位于 `tests/test_workflow.py`。模块任务需在前置契约可用后按依赖顺序实施，包含集成和稳定性验收；文档中的验收标准尚未等同于测试通过。
