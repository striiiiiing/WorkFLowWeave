# 运行记录与存档模块：提案

## 1. 背景与目标

依据 [总体提案](../../proposal.md) §3 和 [总体设计](../../design.md) §1.6、§4.1–§4.2，保存一次 Workflow 的状态及阶段产出。
采集输入、分析结果、最终输出和通知回执属于同一个 session，需要可追溯且能独立查询。
恢复与历史采集必须使用当时保存的内容，不能重新执行原始来源或套用后来修改的配置。

## 2. 首版范围

- 为每次运行建立合法唯一 session ID，持久化创建时间、状态、阶段和 Workflow 关联。
- 保存来源及分支摘要、投递记录、错误、内容索引与可恢复范围。
- 接收统一的 `WorkflowSnapshot`，保存运行时的完整有效配置。
- 按 `BackupPolicy` 控制 `snapshot/collection/analysis/final` 四个内容阶段。
- 管理记录始终保存，内容备份关闭不等于运行历史消失。
- 采集备份保留共享输入及来源结果，分析备份保留有序分支结果及失败信息。
- 最终输出进入通知阶段后冻结，已发送输出不能在恢复中改变含义。
- 提供协程形式的创建、查询、列表、更新、内容存取、可用性检查及过期清理。
- 内容写入成功后再更新索引，读取时验证哈希、长度、格式与 JSON 完整性。
- 区分备份关闭、范围排除、尚未生成、文件缺失、过期、损坏和写入失败。
- 按配置清理过期内容，保留管理记录及过期原因。
- 将启动时遗留的运行记录标为中断，交由 Workflow 决定显式恢复。

## 3. 职责边界

本模块提供持久化与检索能力，不推进执行图，不重新采集、不调用 AI、不发送通知。
Workflow 决定恢复入口、失败策略、哪些分支继续及哪些目标补发。
历史 Collector 负责最近次数、时间范围及 token 预算选择；存档模块只提供已有数据。
没有历史是明确的空查询结果；历史内容损坏是错误，不能包装为空结果。
运行状态、业务成功、投递成功与备份完整性分开表达。
模型调用成功但备份失败，或邮件发送失败，都不能抹去已保存的其他结果。
管理记录不可写时必须报告存档不可用，不向调用方声称 session 可以恢复。
首版不依赖仅在内存中的 LangGraph checkpoint，不提供跨进程事务或自动远程备份。

## 4. 验收标准

- [x] 重建 Store 后仍能读取相同 session 状态、配置快照与阶段产出。
- [x] 关闭备份或排除指定阶段后，运行记录仍存在，缺失原因可查询。
- [x] 文件未写完或原子替换失败时，索引不能指向未完成的新内容。
- [x] 内容被删除、篡改、截断或过期时返回不同原因，不伪造可恢复状态。
- [x] 单个阶段写入失败保留其他阶段，并留下可供 Workflow 执行停止/继续策略的记录。
- [x] 多个协程更新不同 session 不互相覆盖，同一 session 的索引和状态更新串行化。
- [x] 进入通知阶段后的 final 不允许用不同内容覆盖，成功回执可逐条持久化。
- [x] 恢复缺少必要材料时明确报告缺失阶段，读取历史不会调用原始采集源。
- [x] 过期清理跳过运行中的 session，管理记录保留且查询显示过期原因。
- [x] 启动扫描将遗留 `running` 记录标记为 `interrupted`，不擅自恢复执行。
- [x] 所有磁盘等待移交工作线程，取消时不遗留越过后续操作的后台写入。
- [x] 文件故障测试使用临时目录，无需真实模型、网络或邮件服务。

## 5. 交付与依赖

交付 `logagent/archive.py` 及对应测试，复用配置模块 `logagent/models.py` 的公共模型。
配置模块先交付 `WorkflowSnapshot/BackupPolicy/SessionRecord` 与公共错误契约。
Workflow、历史 Collector 和交互模块通过本模块入口访问 session，不直接改写存档文件。
按模块任务完成实现与测试后独立提交；后续执行器更换仍复用相同阶段数据与格式版本。
