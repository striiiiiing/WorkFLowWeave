# Channel 网关模块提案（v0.1）

本模块依据 [根 proposal.md](../../proposal.md) §2.1「channel 网关模块」、§3「验收标准」及 [根 design.md](../../design.md) §1.3、§4.2。详细契约与测试场景见 [design.md](./design.md)。

## 1. 要解决的问题

Workflow 完成采集和分析后，需要按照用户指定的输出顺序向一个或多个目标发送通知。平台协议、连接和失败处理不应散落在 Workflow 内部；某个目标失败也不能使已经完成的分析结果或其他目标的成功记录消失。

首版 Workflow 只需要单向通知。用户未来进行双向 Agent 对话时，Workflow 的主动通知不能切换正在进行的会话，因此需要从一开始保留明确的能力边界。

## 2. 本模块交付范围

- 提供轻量 `BaseChannel` 的启停契约，以及增加 `publish()` 的 `NotificationChannel`。
- 提供 `ChannelManager`，负责发现类型、验证实例、管理生命周期和返回逐目标投递记录。
- 启动时发现 `plugins/channels/*.py`，支持单文件注册多个通道；插件级配置通过同名 JSON 供给，按文件隔离注册失败。
- 内置 `file`，将通知以 Markdown 追加到指定文件；共享文件的并发写入保持每条消息边界。
- 内置 `email`，使用 SMTP、明确的 STARTTLS/SSL 配置、环境变量凭据和配置收件人发送通知。
- 按输出声明顺序、目标配置顺序执行，提供有限重试、超时、取消和逐条成功/失败结果，保留部分成功。
- 保留通知、控制和会话能力的扩展位置；本版只实现通知，不启动接收或 Agent 消费循环。

## 3. 协作边界

| 协作对象 | 本模块输入或输出 |
| --- | --- |
| Workflow | 接收确定的 `Notification` 及目标快照，返回 `DeliveryResult`；正文、发送策略和 session 汇总由 Workflow 决定 |
| 配置与资源管理 | 验证平台 schema 和通知能力；配置存取、引用和快照由配置模块负责 |
| 运行记录与存档 | 网关不直接写入存档；Workflow 可逐条投递并立即保存回执，恢复时跳过已成功组合 |
| 服务启动入口 | 负责装配并协调 Manager 启停，等待或取消运行后回收平台资源 |

本模块借鉴 QwenPaw 解读中的职责分离：注册表负责类型，Manager 负责实例和生命周期，平台类负责协议。首版不实现双向会话、控制指令、消息队列持久化、平台热更新或完整 Agent 框架。

## 4. 验收标准

1. 空插件目录下仍可配置 `file/email`；导入失败、无效声明和重复名称按文件隔离，其他有效通道可继续使用。
2. 未知选项、错误平台能力和无效目标配置在执行前给出可理解的字段错误；禁用目标不实例化或发送。
3. 两个输出与两个目标的调用及返回顺序严格按输出后目标展开；部分失败不丢失此前成功，也不删除已经完成的业务结果。
4. 文件通知保留已有内容；两个实例并发写入同一文件时每条消息完整，不发生字节交错；不可写目标产生明确失败。
5. SMTP 使用配置的连接模式、凭据引用和收件人，正确编码中文；测试全部使用模拟或本地 SMTP，不主动向真实邮箱发送。
6. 重试次数有限，永久错误不反复重试；SMTP 可能已接收但确认未知时保留不确定性，不宣称恰好一次投递。
7. 取消后不发送后续组合，关闭时回收在途任务；单个实例的启动或停止错误不阻止其他实例回收。
8. Workflow 恢复使用原输出和原目标配置，已保存的成功投递不自动重发；失败投递可以明确补发。

## 5. 交付与依赖

实现位于 `logagent/channels/`，共享模型位于 `logagent/models.py`。模块依赖公共模型及配置快照契约，可以用临时文件、测试插件和模拟 SMTP 独立验收；完整的恢复与部分成功归档由 Workflow 集成测试覆盖。完成详细设计后编写本模块 `tasks.md`，按任务验收与提交。
