# `design.md` 接口契约解读

本文解释 `openspec/changes/configurable-collection-analysis-workflow/design.md` 第 3 节“接口契约”。它回答三个问题：模块之间传递什么数据、每个接口负责哪一步、发生异常时调用方应该如何处理。

## 1. 先建立整体认识

一次 Workflow 运行可以抽象为：

```text
读取资源 → 固定配置快照 → collect → analyze → aggregate → notify → finish
```

每一步都有清晰的边界：

- **配置与资源管理**保存资源，并在运行开始时生成不可变的 `WorkflowSnapshot`。
- **数据采集模块**执行一个来源，返回一个明确状态的 `CollectionResult`。
- **AI 模块**执行一次明确分析，返回 `AnalysisResult`。
- **Channel 网关**把 `Notification` 投递到目标，逐目标返回 `DeliveryResult`。
- **存档模块**保存 session、快照和各阶段正文，使运行可以查询或恢复。
- **Workflow 模块**编排顺序、并发、失败策略和恢复；它不重复实现上述模块的协议。
- **API/CLI**是调用入口，负责把 HTTP 或命令行请求映射到这些服务。

因此，接口契约不仅是 Python 方法签名，也包括状态枚举、字段约束、错误含义和持久化规则。

## 2. 公共数据和错误契约

### 2.1 所有模型的共同规则

公共模型位于 `logagent/models.py`，配置用 JSON 表达，时间使用带时区的 UTC ISO 8601。输入模型拒绝未知字段，ID 只能包含 1–80 位 ASCII 字母、数字、下划线或短横线，不能直接当作任意文件路径。

`options`、`setters` 和 `model_options` 是扩展容器，但不表示可以随意添加字段：它们仍需分别通过 Collector、AI 或 Channel 模块的 schema 校验。超时和间隔必须是正数，并发至少为 1，重试次数是非负整数。

### 2.2 主要对象怎样配合

| 对象 | 用途 |
| --- | --- |
| `SourceConfig` | 描述一个具体数据源实例，包括 Collector、选项、Setter 和空结果/失败策略。 |
| `AIConfig` | 描述模型提供方、模型、提示词、工具、参数和超时。凭据只保存环境变量名。 |
| `ChannelConfig` | 描述一个通知目标、目标参数、超时、重试次数和是否启用。 |
| `WorkflowDefinition` | 用有序列表声明来源、分析任务、可选 fan-in 和通知目标，并配置并发及失败策略。 |
| `CollectionResult` | 一个来源的采集结果，区分成功、空、过滤后空、缺失、失败和超时。 |
| `AnalysisResult` | 一个分析任务的成功、失败、超时或取消结果。 |
| `Notification` | Workflow 已经确定的待发送输出，带稳定的 `output_id`。 |
| `DeliveryResult` | 一个输出投递到一个目标后的回执，包含状态、尝试次数和错误。 |
| `SessionRecord` | 一次运行的管理记录，包含阶段、来源/分析状态、投递回执、备份索引和恢复信息。 |
| `WorkflowSnapshot` | 运行时使用的完整配置副本，包含 Workflow 及已展开的来源、AI、Channel 配置。 |

`ErrorInfo` 统一表示错误：`code` 是机器可识别的错误码，`message` 是可读说明，`details` 保存字段路径或诊断信息。公共异常 `LogAgentError(code, message, details)` 不包含凭据、秘密或任意堆栈。

### 2.3 HTTP 错误如何映射

| 状态码 | 典型含义 |
| --- | --- |
| 422 | 请求字段、schema 或 Workflow 语义无效。 |
| 404 | 直接请求的资源或 session 不存在。 |
| 409 | ID 冲突、引用冲突、状态冲突或恢复材料不足。 |
| 429 | 有界运行队列没有容量。 |
| 503 | 存档不可用、服务未就绪或正在关闭。 |

触发接口返回成功，只表示运行请求已接受；模型失败、采集失败等异步业务错误要写入 `SessionRecord`，不会被伪装成触发请求的 500。

## 3. 配置与资源管理接口

### 3.1 `ResourceStore`

```python
ResourceStore(root, *, base_dir=None)

save(kind, model, *, mode="upsert")
get(kind, id)
list(kind)
delete(kind, id)
resolve(definition)
snapshot(workflow_id)
```

所有方法都是协程，磁盘操作放到工作线程，避免阻塞事件循环。`kind` 只允许 `sources`、`setters`、`ai`、`channels`、`workflows`。

- `save` 支持 `create`、`replace`、`upsert`。存在性检查和写入共用同一把操作锁，成功后才替换旧文件。
- `get` 返回独立对象；缺失、JSON 损坏和 schema 无效要报告不同原因。
- `list` 按 ID 稳定排序，不能把临时文件或损坏资源默默当作不存在。
- `delete` 会检查反向引用。仍被 Workflow、模板、分析任务或 Channel 列表引用时返回冲突。
- `resolve(definition)` 只读解析尚未保存的 Workflow，供完整校验使用，不写入资源。
- `snapshot(workflow_id)` 在一致性边界内解析全部引用并返回深拷贝。

### 3.2 为什么必须使用快照

快照包含 `workflow`、按 ID 索引的 `sources`、`ai`、`channels` 和 `created_at`。来源的 Setter 已经把模板展开：模板值先复制，实例同名值覆盖；执行阶段不再读取模板。

运行开始后，后续阶段只使用这份快照。即使用户随后修改模型、通知地址或 Setter 模板，当前 session 的含义也不变；恢复同样只能使用存档中的原快照，不能偷偷换成最新配置。

## 4. 数据采集接口

### 4.1 Collector 和 Manager

```python
class BaseCollector:
    name: str
    options_model: type
    setters_model: type

    async def collect(options, setters, context) -> list[dict]: ...
    def count(items) -> int: ...

class CollectorManager:
    register(collector)
    discover(path, plugin_config)
    describe()
    validate(source)
    async collect(source, context) -> CollectionResult
```

`BaseCollector`只负责一个来源的读取和来源内部处理；它不负责调度、重试、持久化或 Workflow 的 `stop/skip` 决策。`CollectionContext` 注入存档只读入口、工具日志路径以及 Workflow/session 标识。

`CollectorManager.collect` 返回的状态必须诚实区分：

| 状态 | 含义 | Workflow 使用的策略 |
| --- | --- | --- |
| `success` | 有可拼接的有效内容。 | 接入共享输入。 |
| `empty` | 来源范围内没有原始记录。 | `on_empty`。 |
| `filtered_empty` | 有原始记录，但 Setter 处理后没有内容。 | `on_filtered_empty`。 |
| `missing` | 插件、文件或历史所需内容不存在。 | `on_missing`。 |
| `failed` | 来源异常、权限错误、损坏或格式错误。 | `on_error`。 |
| `timeout` | 来源整体超时。 | `on_error`。 |

`count` 与 `selected_count` 分别表示处理前和处理后的计数，不能把分组数冒充条目数。失败不能只返回空列表来隐藏原因。

### 4.2 插件发现和 Setter

启动时扫描 `plugins/Collectors/*.py`。插件导出统一的 `register(registry)`，每个文件先写入临时注册表，完成导入、声明、schema 和名称冲突检查后一次性提交。因此一个文件失败不会留下半个插件，其他文件仍可用。

Setter 的处理顺序固定为：计数 → 过滤 → 稳定排序 → 字段投影 → 移除无内容记录 → 分组/格式化 → 再计数。可用字段和操作由 Collector 声明；未声明的 `group_by` 等能力必须拒绝，不能由通用模板越权开启。

## 5. AI 执行接口

```python
class AIService:
    validate(config)
    async execute(config, prompt, input_text, *, task_id, context=None) -> AnalysisResult
```

`validate` 只校验，不请求真实模型。`execute` 每次处理一个明确任务，使用调用方传入的配置副本和完整输入。提示词中出现 `{input}` 时进行字面替换；没有占位符时把输入追加到提示词末尾。系统提示词作为独立的 system 消息。

首版支持离线 Mock 和 HTTP 兼容聊天模型。模型配置拒绝 `temperature`、`top_k`，也不允许 `model_options` 覆盖服务控制的 `model/messages/tools/stream`、认证和超时。工具必须是已注册名称，参数先过 JSON schema 校验，禁止从配置文本执行任意 shell。

工具调用有边界：默认最多一轮、每次分析最多八次、单工具最多十秒，结果最多 64 KiB，总时长不能超过 `AIConfig.timeout`。取消要向上传递，不能把取消伪装成普通失败；网络、模型协议和工具错误则转换为带原因的 `AnalysisResult`。

## 6. Channel 网关接口

```python
class BaseChannel:
    async start()
    async stop()

class NotificationChannel(BaseChannel):
    async publish(notification)

class ChannelManager:
    register(channel)
    discover(path, plugin_config)
    describe()
    validate(config)
    async start(configs=())
    async stop()
    async publish(configs, notifications) -> list[DeliveryResult]
```

`BaseChannel`描述平台能力和 `options` schema；首版 Workflow 目标必须具备 `notification` 能力。`validate` 不发送探测消息，凭据或连通性问题可在启动/投递时发现。

`publish` 按输出声明顺序、再按目标配置顺序执行，每个输出与目标组合独立返回：

| 状态 | 含义 |
| --- | --- |
| `success` | 平台确认成功；文件已完整写入并 flush，SMTP 表示服务器已接收。 |
| `failed` | 平台明确失败或运行期配置无效。 |
| `timeout` | 本次尝试超时，不能据此断言一定未送达。 |
| `skipped` | 目标 `enabled=false`，尝试次数为 0。 |

最大尝试次数为 `1 + retries`。永久错误不重试；SMTP 发送后断连等不确定情况在 `error.details.delivery_uncertain=true` 中标记，不自动重发，避免重复通知。

## 7. 存档接口

```python
ArchiveStore(root)

create(workflow_id, snapshot, backup)
get(session_id)
list(workflow_id=None, limit=100)
update(session_id, **changes)
save_artifact(session_id, name, content)
load_artifact(session_id, name)
availability(session_id)
mark_interrupted()
expire()
```

一个 session 目录包含 `record.json`，以及按备份策略选择保存的 `snapshot.json`、`collection.json`、`analysis.json`、`final.json`。管理记录始终保存，阶段正文可以关闭备份或因故障缺失。

阶段正文格式固定：

- `snapshot`：`WorkflowSnapshot`；
- `collection`：`{"shared_input": str, "results": list[CollectionResult]}`；
- `analysis`：`{"order": list[str], "results": list[AnalysisResult], "events": list[dict]}`；
- `final`：`{"outputs": list[Notification], "fan_in": AnalysisResult | null}`。

正文写入后才更新索引，并记录 SHA-256、大小、写入时间和可选过期时间。读取时校验索引、文件、长度、哈希和 JSON 结构；`missing`、`expired`、`corrupt`、`write_failed` 等原因必须保留，不能把损坏内容当成空结果。

## 8. Workflow 服务接口

```python
class WorkflowService:
    async validate(definition)
    async save(definition)
    async trigger(workflow_id) -> SessionRecord
    async wait(session_id) -> SessionRecord
    async resume(session_id) -> SessionRecord
    async cancel(session_id) -> SessionRecord
    async shutdown()
```

首版执行图固定为：

```text
collect → analyze → aggregate → notify → finish
```

`collect` 按来源声明顺序整理结果并拼接共享输入；`analyze` 的每个分支接收完全相同的共享输入，并发完成也不能改变最终声明顺序；`aggregate` 根据 fan-in 顺序组合分支和可选的 `$input`；`notify` 先把最终输出冻结，再逐条投递并立即保存回执。

来源的四种策略分别处理 `failed/timeout`、`missing`、`empty` 和 `filtered_empty`。所有来源都无内容时，`on_all_empty=skip` 会直接结束，不调用 AI 也不发送通知；`stop` 则以失败结束。分析分支失败是否阻断下游由 `analysis_failure` 决定，`send_partial` 决定是否发送成功分支的部分输出。

`trigger` 只接受 Workflow ID，不接受临时配置覆盖；它创建 session 并排队，返回的 `SessionRecord` 不代表业务完成。`wait` 只等待，不因调用方取消等待而取消运行；`cancel` 会等待取消状态写回；`shutdown` 停止接收新任务并回收后台任务。

恢复有严格边界：原快照和所需阶段正文必须可读。已有成功分析不能只凭摘要重跑，成功通知也不会自动重发。最终输出冻结后，`resume` 只补发失败或尚未发送的目标；需要重新分析时必须显式创建新的 `/run` session。

## 9. API、CLI 与应用生命周期

API 使用 `/api` 前缀，主要路由包括：

| 路由 | 作用 |
| --- | --- |
| `/{kind}` | 资源列表、创建、读取、替换和删除。 |
| `/plugins` | 查询 Collector/Channel 能力和发现诊断。 |
| `/workflows/{id}/run` | 异步触发一次运行，返回 202 和 session 地址。 |
| `/sessions`、`/sessions/{id}` | 查询运行记录。 |
| `/sessions/{id}/artifacts/{name}` | 读取四种固定阶段正文。 |
| `/sessions/{id}/resume`、`/cancel` | 恢复或取消运行。 |
| `/health` | 查询服务就绪状态。 |

`artifacts/{name}` 只接受 `snapshot/collection/analysis/final`，不能借此读取任意文件。创建或修改 Workflow 必须先经过完整语义校验，再落盘。

CLI 的 `serve` 启动 FastAPI/uvicorn，`init` 生成离线样例，其余资源、运行和查询命令通过 HTTP 调用 API。CLI 不直接执行 Workflow，也不绕过业务校验。

应用启动时依次读取系统配置、初始化 Store、扫描插件、创建共享客户端、启动 Channel 和调度器，最后才标记就绪。关闭时先停止新触发，再取消/等待运行，随后关闭 Channel、模型客户端和后台任务。

## 10. 一个完整例子

假设 Workflow 有两个来源、两个分析任务和一个文件通知目标：

1. `ResourceStore.snapshot("daily_review")` 固定所有配置，`ArchiveStore.create` 建立 session。
2. 两个 Collector 返回 `success` 和 `filtered_empty`。Workflow 按策略跳过后者，仍按声明顺序拼接前者文本。
3. `summary` 和 `risks` 分支同时调用 `AIService.execute`，两者收到逐字相同的共享输入。
4. fan-in 按 `["summary", "$input", "risks"]` 组合结果，生成 `output_id="final"`。
5. Workflow 设置 `output_frozen=true`，ChannelManager 投递文件并保存 `(final, local_notice)` 的成功回执。
6. 如果进程在另一个目标投递前中断，恢复时复用原 `final`，跳过已有成功回执，只处理未完成目标。

这个例子体现了契约的核心：配置在开始时固定，阶段结果有明确状态，顺序由声明决定，失败事实被保留，恢复不会悄悄改变原运行的输入或输出。

## 11. 阅读和实现时最容易犯的错误

- 把 `empty`、`filtered_empty`、`missing` 和 `failed` 都写成空列表，导致 Workflow 无法执行正确策略。
- 用分支完成先后顺序拼接输出，破坏用户在配置中声明的顺序。
- 运行中重新读取 ResourceStore，造成同一 session 混用新旧配置。
- 只保存摘要、不保存成功阶段正文，却声称可以恢复。
- 把 SMTP 超时当作确定失败并自动重发，造成重复通知。
- 让 CLI 直接读存档目录或执行 Workflow，绕过 API 和统一校验。

只要遵守“快照固定、状态诚实、顺序稳定、错误结构化、回执及时持久化”这五条原则，就能正确理解并实现本节接口契约。
