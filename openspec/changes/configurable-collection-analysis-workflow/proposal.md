# 可配置的多源采集与 AI 分析 Workflow

## 1. 背景和目标

### 背景

其实很多时候，人们使用类OpenClaw的工具时，其实更多的只是在使用定时任务，且很多时候还只是对于某些固定源头的新内容进行分析，而其实根本用不到很多Agent功能，那么为什么不直接以这种触发任务固定源头的任务为核心重新设计呢？而只是单纯的Workflow很多时候也是不够用的，很多时候我们会期望去进一步的讨论，所以这个新的产品期望结合这个场景的各个需求，给出一个更好的方案

### 目标

这个工具的目标主要面向用户的定时任务这些固定触发的场景，提供一个易配置且节约费用的workflow，其输出可以独立使用或接入其他 Agent，同时提供后继进一步讨论的轻量Agent，项目内提供轻量对话 Agent，用于围绕结果继续追问、分析和补充查询；采集配置与 AI 配置可在两者之间复用。

以易于扩展的采集器为基础，构建用户详细配置、稳定执行的 Workflow：编排全部采集内容，将同一份输入交给多个具有不同任务或提示词的 AI 分支，按需汇聚结果并发送通知。默认保存采集输入和处理结果，使失败恢复及后续对话能够继续使用当时的数据。

这个工具期望有着很小的硬件需求，以求在更弱的服务器上都可以运行

### 目标用户

主要使用固定触发任务，且苦恼token费用的个人开发者与自托管用户

## 2. 功能和范围

### 2.1 做什么（本期）

以下模板尽可能解耦

#### 数据采集模块

- 实现数据采集模块，用户只要运行前在插件文件夹的Collectors文件夹内添加自己的Collector文件，就可以自动添加新的Collector

  - Collectors应该作为协程，如果它有需要，可以在实现时再开后台线程
- 配置区分为系统级配置和插件级配置
- 采用一个数据源插件，给系统注册多个数据源可选项，以供WorkFlow模块选择
- 用户可以选择按照什么字段分组，选择哪些字段等等Collector提供的功能。这部分调用用户添加的自己的Collector

  - 这里类似于Setter 注入，要注入了Setter才可使用，Setter若用户点击保存为模板，可以保存下来，以便用户复用

#### WorkFlow模块

- 触发可以是内置定时器，也可以是外部的触发，比如WebHook，但是外部的触发这里下一版再写
- 对用户选择好的数据采集源后，提供细化的配置
  - 部分是整体的，比如按照什么进行顺序，对于失败的数据采集源如何处理，比如是否添加一个yaml添加上每个数据源多少份，计数由具体数据源的方法提供
  - 部分是单独的，比如以上的Collector提供的功能
- 为用户提供零代码的workflow拼转服务，采用fan-out——fan-in，fan-out内有多个分析任务，可以采用不同的提示词，不同的模型，不同的模型配置（比如思考与否，可以添加上Json以便用户自定义），不采用温度和top_k，因为这些已经过时了
  - fan-out进入的是所有的数据源拼转好后的文本（未来可能添加上图片）
  - fan-out后，再次实现拼转服务，可以选择将前一步的拼转好的采集源放到某一处，当然，这里这个文本作为一个整体而非是可以移动的
- 可以选择发送的channel，可以选择多个channel
- 自动备份，对于进入的编排好的采集源备份，对于第二步fan-out后的进行备份，对于最终fan-in结果也进行备份
  - 对于这样一个session，应该按照session来备份

#### 简易Agent模块

- 带有Model及其配置、工具和系统提示词，这个是需要实现的，提供给前面的WorkFlow模块用的
- 后继可以将将WorkFlow模块的结果，前面添加上可以是系统默认，可以是用户指定的提示词作为系统提示词的部分（即系统提示词模板填充），然后允许用户在双向的channel进行进一步的讨论。这一版不实现，仅仅留有接口

#### channel网关模块

- 用户在运行前在插件文件夹的channel文件内添加自己的channel文件，就可以自动添加新的channel

  - channel应该作为协程，如果它有需要，可以在实现时再开后台线程
- 借鉴其他成熟Agent的channel的管理，这里借鉴的是Qwenpaw的
- 将channel按能力区分

  > 我认为对于workflow，实际上是只要有通知，是单向的，而agent应该是另外一个双向的交流，否则用户体验会很糟糕，先在交流着，然后一个消息发过来，然后对话就切换了 当然，也不一定要完全锁死进入的信息，可能可以在workflow那部分的网关进行一些系统配置相关，当然，我希望这个是可选项，如此便于利用一些只读的网关
  >

  - NotificationChannel，实现`publish()`，适合只读 Webhook、邮件、机器人推送，用于WorkFlow的通知
  - ControlChannel，实现`publish()`的同时，实现对指令的receive()，当然，这个后面再实现
  - ConversationChannel，实现 `receive()`、`reply()` 和会话路由，显然，它也是NotificationChannel
  - 一个插件可以同时注册三种不同的channel

#### 交互模块

- channel网关层可以直达内部
- 用户通过API服务进行交互
- 通过Cli进行启动，Cli还有一些简单配置，Cli层应该要很薄，主要还是包装成HTTP发送给API服务
- 通过 json 文件进行配置

## 3. 验收标准

### 功能验收

1. 系统启动时能够读取系统级配置和插件级配置，并自动发现 `Collectors` 文件夹中的有效 Collector；重复注册、配置无效或加载失败时给出可识别的错误，不影响其他有效 Collector 的发现。
2. 首版至少提供以下采集源：

   - 可选的指定 Workflow 历史记录，用于为当前 Workflow 提供记忆；

     - 提供按最近多少次，或者按多少时间内这些子类的选项
   - 本工具自身的运行日志。
   - 一个Mock数据源

   每个采集源都能以协程方式执行，并能暴露自己的可配置选项、字段选择、分组方式及计数结果。用户保存的 Setter 配置可以在后续 Workflow 中复用。
3. 用户能够创建并保存一个 Workflow，选择多个采集源并填写各自的来源专属配置，同时设置整体顺序、采集结果的编排方式以及单个来源失败、缺失或无内容时的处理策略。历史记录采集支持按最近次数、时间范围或 token 限制进行选择。
4. Workflow 能够将所选采集源整理成一份共享输入，再把这份完整输入送入多个分析任务。不同分析任务可以分别配置提示词、模型和模型配置；fan-out 的任务结果能够按配置进入可选的 fan-in，或分别作为输出。
5. Workflow 能够按配置选择一个或多个 channel 发送结果，并保持用户指定的输出顺序；采集内容、fan-out 结果和 fan-in 结果都能按同一 Workflow session 进行备份，且备份开关和范围可配置。
6. Workflow 历史记录能够被再次选作采集源，使后续运行可以读取指定范围的历史数据；没有历史数据时应返回明确的空结果状态，而不是伪造内容。
7. Channel 网关至少提供：

   - 向指定邮箱发送邮件的 NotificationChannel；
   - 将通知追加到指定文件尾部的 Mock NotificationChannel。

   Workflow 只依赖单向通知能力，不需要启动双向 Agent 对话即可完成运行和发送。
8. AI 模块能够被 Workflow 的分析任务复用，并能提供模型及其配置、工具和系统提示词；同一套 AI 配置可以被后续 Agent 复用。当前版本不要求实现完整的双向 Agent，但应保留 Workflow 输出被后续 Agent 使用的关联信息。
9. API 能够完成 Workflow 的基本配置、保存和触发操作，并能查询运行历史及备份结果；CLI 只提供启动和必要的调用入口，不重复实现业务逻辑。

### 性能验收

- 在首版验收环境中连续运行十分钟不发生未处理异常导致的自动崩溃；24 小时稳定性作为后续验证目标。
- Collector 和 Workflow 的主要等待操作采用协程，单个来源或单个分析任务的超时不会无限阻塞整个服务。
- 验收运行期间记录系统 CPU 占用、内存占用和硬盘占用，作为下一版本制定资源指标的基线；本期不以固定数值作为跨硬件环境的通过门槛。
- 在多个 fan-out 分支同时运行时，分支能够并行推进；配置为关闭或限制并发时，实际并发行为与配置一致。
- 使用已备份的采集内容读取历史或继续处理时，不应因读取历史而重新请求原始采集源。

### 边界场景

- Collector 文件不存在、无法导入、重复注册或来源专属配置缺失时，系统应记录明确原因，并按照 Workflow 配置跳过并在日志里提示；其他 Collector 仍可被发现。
- 单个来源成功但没有条目、经过字段选择或过滤后没有条目，以及所有来源都没有内容，应分别记录并执行对应策略；不得把失败伪装成空结果。
- 历史记录超过次数、时间或 token 限制时，只能按配置截取或报告超限，不能静默破坏输入边界。
- 某个 fan-out 分析任务失败时，其他任务的结果仍应按配置保留；fan-in 开启时用户可选标明输入不完整，fan-in 关闭时按用户配置决定允许分别发送成功结果。
- 采集备份或分析结果备份失败时，系统应标记该 session 不可完整恢复，并按照配置停止或继续
- 邮件发送失败、Mock Channel 文件不可写或部分 channel 失败时，已完成的采集和分析结果仍应保留
- Workflow 被中断后再次处理时，使用已保存 session 的内容和配置；保存被关闭或备份已过期时，应明确提示无法恢复的范围。
- API 收到不完整、未知或不符合 Collector schema 的配置时，应返回可理解的校验错误，不启动半配置的 Workflow。

## 5. 术语定义

|术语|定义|
| -------------------| ---------------------------------------------------------------------------------------------------------|
|Collector（采集器）|封装一种数据来源访问能力的插件，可以通过 CLI、API、文件或其他方式获取数据，并提供自己的配置项和结果字段。|
|数据源实例|某个 Collector 加上一次具体的连接、范围和查询设置，例如一个 GitHub 仓库或一个 RSS 地址。|
|系统级配置|对整个服务生效的配置，例如运行参数、公共连接信息、插件位置和默认策略。|
|插件级配置|随 Collector 或 Channel 插件提供的配置，用于声明该插件可用的来源、字段和选项。|
|Setter|Collector 暴露的可配置设置项或设置注入能力；只有 Collector 声明并接收的 Setter 才能被 Workflow 使用。|
|Workflow|用户预先配置并按固定流程执行的采集、编排、AI 分析、结果汇聚和通知任务。|
|Workflow session|一次 Workflow 运行的完整上下文标识，用于关联采集输入、分析结果、fan-in 结果、通知状态和备份内容。|
|采集结果编排|按用户配置选择字段、分组、排序、过滤和拼接多个来源结果，形成后续分析共同使用的输入。|
|分析任务|对共享采集输入执行一次明确目标的 AI 处理，包含任务说明、提示词、模型和模型配置。|
|fan-out|将同一份编排后的共享输入分发给多个分析任务；本期不表示按采集源分别分配输入。|
|fan-in|对多个分析任务的结果进行再次拼接或分析的可选步骤。|
|AI 配置|可复用的模型、连接、凭据引用、模型参数、工具和系统提示词设置。|
|备份|对某个 Workflow session 的采集输入、分析结果或最终结果进行持久化保存，以便历史读取和失败恢复。|
|NotificationChannel|只提供向外发布消息能力的 channel，用于 Workflow 通知，例如邮件或 Mock Channel。|
|ControlChannel|在发布能力之外接收系统指令的 channel；本期只保留设计余地。|
|ConversationChannel|提供接收、回复和会话路由能力的双向 channel；本期只保留与 Agent 对接的设计余地。|
|ChannelManager|负责发现、注册、配置、管理和调用多个 channel 实例的管理模块。|
|BaseChannel|channel 的通用基类，约束公共生命周期和能力边界，具体平台行为由插件实现。|
|简易 Agent|面向后续对话的轻量执行者，可复用 AI 配置、工具及 Workflow session；本期不实现完整的双向 Agent 功能。|
