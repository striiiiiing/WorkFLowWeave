# 可配置的多源采集与 AI 分析 Workflow

## 1. 背景和目标

### 背景

GitHub 更新、每日新闻等信息需要持续采集、整理和分析。现有操作往往是分别调用 CLI 或 API，再手动提交给 AI。来源配置难以复用；分析或对话失败后，按时间窗口采集的内容可能已经变化，重新采集无法还原当时的输入。

### 目标

以易于扩展的采集器为基础，构建用户详细配置、稳定执行的 Workflow：编排全部采集内容，将同一份输入交给多个具有不同任务或提示词的 AI 分支，按需汇聚结果并发送通知。默认保存采集输入和处理结果，使失败恢复及后续对话能够继续使用当时的数据。

Workflow 及其输出可以独立使用或接入其他 Agent。项目内提供轻量对话 Agent，用于围绕结果继续追问、分析和补充查询；采集配置与 AI 配置可在两者之间复用。

### 目标用户

需要定期关注仓库动态、新闻等信息的个人开发者与自托管用户，以及希望通过少量适配代码接入已有 CLI/API 的开发者。

## 2. 功能和范围

### 本期做什么

本期处理顺序如下；采集源是否并行获取，与 AI 分析的 fan-out 是两件事。

```text
Collect sources -> Arrange all collected content -> Shared input snapshot
                                                        |
                       +--------------------------------+----------------+
                       v                                v                v
                 Analysis task A                  Analysis task B   Analysis task N
                       |                                |                |
                       +--------------------------------+----------------+
                                                        v
                                           Optional fan-in -> Notify
```

| 功能范围 | 本期内容 |
| --- | --- |
| 采集器接入与复用 | 采用 `CollectorManager + BaseCollector`，借鉴 Channel 的注册、装配和管理方式。提供方便包装 CLI 的公共能力，首批支持 GitHub 与新闻采集；新闻以用户配置的 RSS/Atom 订阅源作为首版默认范围。采集器自行声明和校验来源专属选项，同一类型可以配置多个来源实例。 |
| 用户详细配置 | 先加载全局配置与可用扩展，再应用用户设置。支持来源启用、查询范围、分页等专属参数，以及处理顺序、内容编排、分组、规则过滤、分支数量、提示词、AI 选择、通知和持久化策略。支持通过配置及 API 管理；网页编辑界面后置。全局与项目本地扩展的发现、冲突及覆盖细节在设计阶段定义。 |
| 固定 Workflow 与 AI 分析 | “固定”指按用户保存的配置运行，不由对话或模型临时决定执行流程。本期所有分析分支接收同一份编排后的完整输入，通过不同任务、提示词和 AI 配置产生结果。配置变更用于后续运行，进行中的运行继续使用启动时的配置。 |
| 可选 fan-in 与独立输出 | fan-in 位于分析分支之后，用户可选择汇聚结果或分别输出；通知中的排列顺序与分支实际完成顺序分开控制。输出无需启动项目内 Agent 即可读取和复用，不要求固定的报告业务对象。 |
| 共享 AI 配置 | 独立模块管理模型提供方、连接与凭据引用、模型参数及调用策略，Workflow 分支、可选汇聚步骤和对话 Agent 均可引用。分支的任务与提示词独立配置；分析执行单元保留替换为预配置 Agent 的能力边界，本期默认使用 AI 调用。 |
| 持久化与恢复 | 默认在 AI 分析前保存实际采集内容及编排后的共享输入，并保存运行配置关联、分析输出和执行状态。分析或对话失败后可使用原快照继续处理，重新采集须作为明确的新操作。用户可配置保存范围、保留期限及关闭保存。 |
| 通知与对话 | 使用 `ChannelManager + BaseChannel` 管理通道。Workflow 只要求单向通知能力，兼容只能推送的通道；对话 Agent 使用独立会话入口。用户主动关联某次运行后继续对话，通知到达不会切换现有对话上下文。接收系统控制命令作为可选扩展，不作为通知通道的必需能力。 |
| 轻量对话 Agent | 可读取已保存的运行输入与结果，并复用采集器查询能力和共享 AI 配置。公共连接配置只维护一份，Workflow 与 Agent 可分别设置查询参数或限制，例如 Agent 只查第一页。 |

字段分组、明确条件过滤、排序和条目计数属于可配置的内容整理能力；语义筛选与解释由分析分支的任务或 Agent 工具承担。采集内容的编排是所有分支共享输入的准备步骤，不受后续 fan-in 开关影响。

来源未配置或不可用、执行报错、成功但无内容、过滤后无内容，以及整次运行无可用内容，应分别记录并按用户策略处理。全局提供默认策略，用户可对单个来源及整个 Workflow 调整跳过、重试、继续、停止和通知行为。

### 本期不做什么

- 不实现按分析分支选择不同采集源、按来源或按条目自动拆分分析输入；这些属于后续扩展。
- 不由对话 Agent 自动生成或动态改写运行图，不建设通用可视化 DAG 编辑器；不限制用户配置来源专属参数及本期支持的处理选项。
- 不建设自主规划、多 Agent 协作平台；替换分析执行单元的接口边界不等于本期交付完整 Agent 编排能力。
- 不实现应用运行日志采集、Drain 模板抽取、通用日志分析或通过对话生成新采集器代码。这些后续可作为 Agent 工具或采集器扩展。
- 不实现新闻全网搜索、任意网页爬取、所有 CLI 的自动适配、插件市场与插件热更新。
- 不实现完整网页管理端、全平台 Channel、多租户权限平台或分布式调度系统；首版以手动及基本定时触发验证完整流程。
- 不让通知自动进入或接管 Agent 对话，不强制用户使用双向通道，也不依赖 Agent 才能完成 Workflow。
- 不承诺 AI 多次生成相同文本；可复现指保留当时的输入及配置依据。不保存或已清理的数据无法保证恢复。
- 本 proposal 不定义完整配置 schema、类接口、数据库选型、节点实现或任务拆解，留待后续设计与规格。

### 技术约束

- 必须使用 LangGraph 编排 Workflow，并使用其状态与检查点能力支持执行恢复。选型依据是显式表达分析分支、可选汇聚及失败恢复，便于验证和展示工程能力；采集器本身保持可独立调用。
- LangGraph 检查点与采集内容持久化分别承担执行恢复和输入留存职责，不能假定采用 LangGraph 就会自动保存外部数据。
- Channel 与 Collector 分别使用 Manager 和 Base 抽象，复用注册与配置装配的思路；Collector 不依赖通道会话流程，AI 配置不散落于各采集器。
- CLI 适配统一处理参数、超时、退出状态与结果解析；Workflow 和 Agent 复用明确的查询操作，凭据无需在每个使用处重复配置。
- 单次运行必须采用明确的输入及配置快照。具体存储方案与各配置层覆盖规则在后续设计中确定。

## 3. 验收标准

### 功能验收

1. 可配置一个包含 GitHub 与新闻来源的 Workflow，各来源专属参数经过校验；修改用户配置后，后续运行采用新设置，全局公共连接配置可继续复用。
2. 将全部来源按配置整理为共享输入后，至少两个具有不同任务或提示词的分析分支收到内容相同的输入；各分支可独立选择已配置的 AI。
3. 使用结构化样例按“提交者”分组、按“提交时间”排序，并按明确条件过滤，结果符合配置；条目计数反映实际输出内容。支持配置分支与通知输出顺序，不受完成先后干扰。
4. 分别验证启用与关闭 fan-in：启用时汇聚分析结果，关闭时结果可分别输出；两种方式均可在不运行对话 Agent 的情况下完成通知并读取产物。
5. 默认保存开启时，采集成功后人为使分析失败，再修改外部来源或推进采集时间窗口；恢复处理仍使用已保存的原始输入，不重新采集。Agent 对话失败后，也可再次读取关联运行的数据。
6. Workflow 与 Agent 能引用同一采集连接与 AI 配置，同时分别应用自己的查询设置；Agent 的第一页限制不改变 Workflow 的查询范围。
7. 通知到达正在对话的用户时，会话上下文保持原关联；只有用户明确关联另一运行才切换。只有发送能力的 Channel 也能完成 Workflow 通知。

### 性能验收

- AI fan-out 支持配置并发上限。在三个无依赖分析分支、每个模拟调用固定耗时 1 秒、并发上限为 3 的受控测试中，五次运行的分析阶段耗时中位数低于 2 秒；并发上限设为 1 时不得出现重叠调用。该基线不计真实采集、模型或通知网络延迟。
- 采集及模型调用受配置的超时和重试次数约束，单个无响应来源不能无限阻塞运行；达到限制后进入所选失败策略。
- 基于已保存输入恢复分析或继续对话时，在未要求补充查询的情况下，对外部采集源的新增调用次数为零。
- 首版不承诺生产环境吞吐量或真实模型响应时延；更大数据量、硬件环境与容量指标在后续规格中确定。

### 边界场景

| 场景 | 验收要求 |
| --- | --- |
| 单个来源未配置、插件或 CLI 不可用 | 与“采集成功但为空”区分，按配置跳过、提示或停止；显式停用的来源不作为故障。 |
| 单个来源报错或超时 | 按配置重试、继续或停止；继续时保留失败标记，不将不完整输入呈现为全部成功。 |
| 单个来源为空或过滤后为空 | 记录对应原因，按配置省略、展示空状态或继续分析其他内容。 |
| 所有来源成功但无内容 | 按配置静默结束或发送无更新通知；不发起无意义的内容分析。 |
| 所有来源失败，或失败与空结果并存且无可用内容 | 按失败策略处理，不能报告为正常的“今日无更新”。 |
| 一个分析分支失败 | 根据配置重试、停止或输出成功部分；启用 fan-in 时明确其输入不完整。 |
| 共享输入超过所选模型上下文限制 | 显式报错或要求调整采集与编排配置，不静默截断，也不暗中为不同分支分配不同来源。 |
| 默认持久化开启但保存失败 | 不将该次输入标记为可恢复；在进入分析前停止并报告保存失败。 |
| 保存被关闭、保存范围不足或快照已过期 | 明确告知无法恢复的范围，不用重新采集的内容冒充原始快照。 |
| 通知失败 | 保留已完成的分析产物，允许单独重试发送，无需重新采集和分析。 |

## 4. 术语定义

| 术语 | 本项目含义 |
| --- | --- |
| Collector / 采集器 | 封装一种 CLI/API 等来源访问能力，可供 Workflow 和 Agent 复用。 |
| 来源实例 | 某个采集器加上具体连接与查询配置，例如一个 GitHub 仓库或一个新闻订阅源。 |
| Workflow | 用户预先配置、运行时按保存配置执行的采集、整理、分析及通知流程。 |
| 共享输入 | 本次运行所有可用采集内容经配置规则编排后的输入；本期每个分析分支均使用这一份内容。 |
| fan-out | 将共享输入分发到多个不同任务或提示词的分析分支，不表示逐采集源独立分析。 |
| fan-in | 可选的分析结果汇聚步骤，不是分析前的采集内容编排。 |
| AI 配置 | 可复用的模型连接、模型参数及调用策略；分析任务和提示词由使用方另行配置。 |
| Agent | 用于推进对话、读取历史输入和调用工具的执行者；也可作为未来分析执行单元的替代实现。 |
| 运行快照 | 某次实际采集输入及关联配置的留存，用于失败恢复、再次分析和后续对话。 |
| Channel / 通道 | 由 ChannelManager 管理的通知或交互适配器；能力按用途选择，通知不要求接收消息。 |
