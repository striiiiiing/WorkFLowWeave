# 前端架构实施设计索引

本 change 执行 [前端架构设计](../design-frontend-architecture/design.md) §1–§12，保留该原文及其 proposal 的历史状态。用户在本轮明确要求按该设计实施，授权范围包括独立分支、先 tasks/DAG、分包委派与中途提交；原文“仅设计/后续实施”的阶段说明不限制本实施 change。这里不复制原文，不新增或改变架构决策。

| 实施主题 | 唯一设计依据 |
| --- | --- |
| 范围、既有规范差异与后端边界 | 原设计 §1、§2 |
| 依赖规则、工厂注入、SFC 职责与最低组件树 | 原设计 §3–§4 |
| 查询、唯一草稿、稳定 Agent 路由作用域及保存结果 | 原设计 §5 |
| 共用/独立数据源、resolve 与使用位置 | 原设计 §6 |
| Agent 历史/当前快照/SSE、轮次隔离、命令与文件 | 原设计 §7 |
| Axios、严格 JSON、503/204、Schema 与安全渲染 | 原设计 §8 |
| 路由、触控、样式及旧目录映射 | 原设计 §9–§10 |
| 独立 change、批次回退、验证与默认值 | 原设计 §11–§12 |

实施拆包、API 交接的具体名称、所有权和验证命令属于执行决策，记录在 [tasks.md](tasks.md) 与其工作包说明中。它们必须服从上述设计，不能用 tasks 暗改产品行为。需要偏离已授权设计时先记录具体冲突并取得同意；一般实现选择和设计内修复直接推进。

这是结构性修复：仅移动文件会保留重复草稿、混合保存目标及跨模块依赖，因此按设计同时拆分控制器和纯模型。DTO 首轮手工按模块单一定义；控制器接收最小 API/时钟/连接依赖，运行时由 app 装配；不增加后端适配层、全局业务缓存或第二套兼容实现。

新增能力增量仅表达设计已规定但仍需明确验收的外部行为；完整回归范围仍包含原设计 §12.1 及既有业务规范。归档前须核对多个活动 change 的能力冲突，不能因本变更文档齐备而宣称其他 change 已验收或自动归档。
